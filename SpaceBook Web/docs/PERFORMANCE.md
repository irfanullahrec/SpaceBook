## Where the time and the size are

- 346 of 9,698 tabs are over 500 KB of HTML, 74 over 2 MB, 9 over 5 MB. By subject, tabs over 2 MB: Class 11 Maths 17, Class 11 Chemistry 11, Class 12 Statistics 8, Class 12 Chemistry 7, Class 12 Physics 5, Class 12 Biology 5, Class 12 Maths 4.
- The worst is a Class 11 Maths lesson: **10.8 MB, 269,106 elements, 6,059 formulas**. Of the size, about 1.9 MB is the MathML copy of the formulas, about 3.7 MB the drawn formulas, and most of the rest is **one `<span>` per word** (so that a word can show its meaning on hover). The lesson is 28 accordion cards of 130-600 KB each, closed unless opened. A browser has to parse and build all 269,000 elements before it can show the first card, even though only the open cards are laid out; on a phone that is seconds and well over 100 MB of DOM.

## What would fix it (not done, and why)

1. **Fill a closed card when it is opened (built, off, partial).** `js/core/lazycards.js` does this for the Maths accordion cards behind the owner flag `lazyCards` (`window.SB_FLAGS.lazyCards` or `localStorage sb_flag_lazyCards = 'on'`; default off). While `switchMathTab` / `switchSubjectTab` draws a tab, the body of every closed card of 4 KB or more is kept as a string and the card gets an empty body; opening the card (or "expand all", or the full-screen button, which clicks the header) puts it in and typesets the formulas. `tests/perf/lazycards.js` draws the same chapters with the flag off and on, opens every card and requires the two pages to be identical (ids with a random part renamed): Class 5 Maths ch. 7, Class 8 Maths ch. 4 and, with `SB_LC_FULL=1`, Class 11 Maths ch. 4 and Class 12 Maths ch. 1. **How much it removes is limited by `sb_structure.js`**: that module reads every lesson card while it plans a chapter and moves the exercise, key-point and SLO blocks out of the lesson into their own tabs, so a body that contains such a block must not be deferred (my first version deferred them: the page after opening every card was no longer the same, exercise blocks reappeared in the lesson). With that rule, on the lesson tab: Class 11 Maths loses 43-54 % of the HTML (10.8 MB -> 5.2 MB for the worst), Class 7 Maths ch. 1 49 %, Class 12 Maths 100 % (3.9 MB -> 10 KB; 24,445 -> 223 elements), Class 5 Maths ch. 8 55 % of the elements, and Class 8 Maths ~0 % (every topic card carries its exercise block). The complete fix is the planned one: let `sb_structure` plan from the data, not from the rendered DOM (Phase 5 / 6), after which every closed body can be deferred. Enable the flag on a phone, open a Class 11 Maths chapter and open and close cards, the full-screen button, a sentence translation and "expand all"; if all is as before, make it the default (set `window.SB_FLAGS = { lazyCards: true }` before the scripts in `index.html`).
2. **One listener instead of a span per word.** The hover meaning could read the word under the pointer from the text node instead of wrapping every word. Same reason.
3. **Drop the duplicate MathML** (about 1.9 MB of that tab) and give each formula an `aria-label`. This trades screen-reader quality for size; it needs a decision and a screen-reader check, so it is not done.
4. Page the "examples" and "exercises" lists of the 41 slow tabs (only the first screen at once).

## Not measured, and needs a person with a phone

Time to interactive and the chapter/tab times on the reference device (Chrome CPU x6 throttling, or a real 2 GB Android), Lighthouse mobile, the DOM's memory, the service worker's first install on a slow connection, the real size of "Search all classes" on mobile data. The budgets above should be signed off by the owner once those exist; until then the honest status is "met in a CPU proxy, unmeasured on a device, with the known outliers above (41 tabs, 22 chapters, 11 cold opens)".
